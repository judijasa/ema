## Status quo (what we are replacing)

Section resolution rules, duplicated in two consumers:

- ema bash `_resolve_target` (ema file, L38-53):
  - EMA_TARGET=local (default): use `[local:<dbname>]` if present, else fall
    back to `[local]`.
  - any other EMA_TARGET: use `<dbname>` if given, else EMA_TARGET itself.
- framework `src/Connectivity/Database.php` `loadConfig()` (L33-43): identical
  rules — `getenv('EMA_TARGET') ?: 'local'`, then `[local:<dbname>]` or
  `[local]`, else `[<dbname>]`.

The section name is the lookup key (dbname -> connection). The DBNAME key
inside sections is vestigial in the framework (buildDsn uses the method
argument dbname); only ema `init tables` reads it.

## Issue 1 — Database.php agnostic to ema

Resolution (agreed): `Database.php` resolves `[$dbname]` by the method
argument in **every** file — section selection is `$target = $dbname` with no
`EMA_TARGET` env var and no fallback. Because the local file is also sectioned
(issue 2), there is no flat-vs-sections shape detection: the rule is literally
`$target = $dbname`. (The `REUTER_LOCAL` flag below selects the **file**, not
the section.)

Current coupling (framework src/Connectivity/Database.php):

    $env = getenv('EMA_TARGET') ?: 'local';
    if ($env === 'local') {
        $target = isset($cnf['local:' . $dbname]) ? 'local:' . $dbname : 'local';
    } else {
        $target = $dbname;
    }

Flag for selecting the **file** (prod `reuter.ini` vs `var/reuter.local.ini`),
not the section (open — deferred until issues 2/3 settle). phprun lets `.env`
override the process env (`set -a; . .env`), so a per-run `REUTER_INI` would
be clobbered. The phprun change was rejected. Candidates:

- (ii) `REUTER_LOCAL=1` read by Database.php (not written to `.env`, so phprun
      cannot clobber it) -> use `$PWD/var/reuter.local.ini`. Recommended.
- (i) stop writing `REUTER_INI` into dev `.env` so `REUTER_INI` itself is the
      per-run flag (fragile: stale `.env` pins it until regenerated).
- (iii) edit the `.env` value per test (clunky).

## Issue 2 — move local connectivity to var/reuter.local.ini

End state (agreed):

- etc/reuter.ini: prod only. One `[<dbname>]` section per prod database,
  generated by gen-reuter (SERVER = hosting server's ZeroTier IP, PORT =
  DEPLOY_DB_PORT).
- var/reuter.local.ini: the dev sandbox, git-ignored. **Sectioned** by dbname
  (`[<dbname>]`), same shape as prod — one resolution rule everywhere. No
  DBNAME key anywhere (the section IS the dbname; see issue 3).
- No template file under etc/: **ema generates/updates** var/reuter.local.ini
  at `ema init db` (local mode, see issue 3) — reuse existing passwords when
  the section exists, generate fresh ones otherwise; write SERVER/PORT/DBMS +
  credentials. (Rejected: a committed etc/reuter.local.ini.template and the
  flat-keys shape.)

Why it is safe:

- prod never reads it: prod .env sets EMA_TARGET=prod and
  REUTER_INI=/etc/<app>/reuter.ini (outside the repo);
- /var/ is already git-ignored (credentials stay machine-local);
- matches the rule in simox doc/2026-08-20-mariadb-instance-per-project.md:
  reuter.ini stays pure connectivity and must not carry infrastructure
  identity;
- one MariaDB instance per project (same doc) makes the `[local:<dbname>]`
  per-db override obsolete.

Touch points (when implemented):

- [ ] framework Database.php — loadConfig(): drop the env branch (issue 1).
- [ ] ema `_resolve_target` / `_load_target` — same branching; error loudly
      when the file/section is missing (no fallback) (issue 3).
- [ ] ema `_cmd_init_db` — explicit-mode branches (see issue 3): local mode
      writes/updates var/reuter.local.ini; prod mode errors on a missing
      section.
- [ ] gen-reuter — stop preserving `[local]`/`[local:<dbname>]` and stop
      writing DBNAME; maintain prod sections only (keep prod credentials
      across runs).
- [ ] docs in all three repos; migrate existing `[local]` sections out.

## Issue 3 — strict, no-default section resolution (ema consumer side)

Direction (agreed): the section header is the **single** database-name
specification — `DBNAME` dies everywhere (gen-reuter stops writing it; the
local file never has it; ema `init tables` gains a dbname arg, issue 5).

### ema init db branch rule — explicit, not inferred

Gap found in review: an earlier wording inferred the branch from section
existence ("missing -> sandbox, exists -> prod"). On a prod server a missing
`[<name>]` would misfire into the sandbox path — creating the db in the prod
instance (after issue 7 the socket points at $DEPLOY_DB_BASE/mysql.sock) and
writing a var/reuter.local.ini into the deployed repo that gets wiped on
redeploy. Wrong on both counts.

Fix: the branch is a property of the machine's mode, not of section absence:

- **Prod mode** (server .env: EMA_TARGET=prod, REUTER_INI=/etc/<app>/reuter.ini):
  `ema init db <name>` requires `[<name>]` to exist; missing -> loud error,
  nothing is written anywhere. gen-reuter writes sections for the whole
  machines.ini roster before databases exist, so a missing section on prod is
  always a misconfiguration.
- **Local mode** (dev machine only: `EMA_TARGET=local`, ema's own machine-mode
  signal — not the framework's `REUTER_LOCAL` file flag from issue 1, which ema
  does not read): missing section -> create the db in the sandbox and append
  `[<name>]` to var/reuter.local.ini (issue 2).

This keeps the prod server safe by construction (its .env says prod, so the
var/ write is unreachable there) and preserves strictness (no default
fallback).

### Superseded options

- a) strict `[env:db]` sections (`[prod:mydb1]`) — conflicts with gen-reuter's
      bare `[<dbname>]` prod sections;
- b) environment-only `[local]` / `[prod]` — needs one shared connection per
      environment and dbname on every command.

Key insight: within one environment, dbname-keyed sections already work (the
prod model). The `env:` prefix only exists because the same dbname can exist
in multiple environments with different connections.

## Issue 4 — ema init commands use root

Clarified: prod root uses unix_socket auth, so `-u root` over TCP/ZeroTier
cannot authenticate. The hardcoded `-u root` is therefore **correct only for
server-local socket creation** and cannot be used from a dev machine against
a prod section. Prod database creation must run on the DB host via the socket
(issue 9). No ema auth change is needed for that path. (The earlier "use the
section admin user over TCP" framing remains a possible but different
approach, superseded by the server-side model.)

## Issue 5 — init tables has no dbname argument

`ema init tables <root-pkg>` takes only the package; it resolves the default
target with no dbname and reads the section's DBNAME key (L180). Under the
redesign it takes a dbname argument like mariadb and init db, and the DBNAME
key is dropped entirely (issue 3).

## Issue 6 — template reference mismatch

ema `_load_target` error message (L61) tells the user to copy
etc/reuter.ini.template, but the ema repo ships etc/reuter.ini itself as a
committed example and no .template. Consumer repos (framework, simox) do have
etc/reuter.ini.template. Cosmetic fix pending.

## Issue 7 — prod .env does not carry MYSQL_UNIX_PORT (PRIORITY)

Problem: the prod `.env` no longer carries `MYSQL_UNIX_PORT` — the
multi-server-deploy change dropped the `MYSQL_*` keys (TCP everywhere; see
php_daas_framework/doc/2026-08-22-multi-server-deploy.md). ema reaches the
instance over the socket only when `MYSQL_UNIX_PORT` is set; otherwise it
falls back to TCP (`-h SERVER -P PORT`) and root over TCP fails (prod root =
unix_socket auth). So "ssh to the DB host and `ema init db <name>`" cannot
work until ema learns the socket path.

Decision (made): **(B)** — the socket path lives in the prod `[<dbname>]`
section, mirroring `[local]`.

- (A) restore `MYSQL_UNIX_PORT` in `.env`, only on the DB host. Reuses the
      existing `_mariadb_args` branch. Caveat: `Database.php` also reads
      `MYSQL_UNIX_PORT`, so on a DB host that also runs the app it would
      switch app connections to the socket (host-pinned-grant risk, issue 8).
- (B) `gen-reuter` writes `MYSQL_UNIX_PORT=$DEPLOY_DB_BASE/mysql.sock` into
      each prod `[<dbname>]` section; ema reads it from the section
      (`_load_target` already evals section keys, and the `[local]` example
      already carries the key). `.env` stays `MYSQL_*`-free, so `Database.php`
      stays TCP-only. Chosen (consistent with the TCP model).

Implemented on the ema side (2026-08-24):
- `_load_target` clears the connection keys (`SERVER`, `PORT`, `DBNAME`,
  `DBMS`, `ADMIN_PASSWORD`, `READER_PASSWORD`, `MYSQL_UNIX_PORT`) before
  evaluating the section, so the section is authoritative and an exported
  `MYSQL_UNIX_PORT` (e.g. the dev shell's) cannot leak into a TCP section.
- `etc/reuter.ini` prod example now carries `MYSQL_UNIX_PORT`, mirroring the
  `[local]` example (parallel `reuter.ini` / `reuter.local.ini` shapes).
- `gen-reuter` (php_daas_framework) writes
  `MYSQL_UNIX_PORT=$DEPLOY_DB_BASE/mysql.sock` into each prod `[<dbname>]`
  section. Also: `_load_target` still hardcodes `etc/reuter.ini` and ignores
  `REUTER_INI` — the prod DB-host flow needs that fixed (issue 2/3).

The env-generation refactor (env.prod -> deploy.conf) is a framework concern
and is tracked separately in
php_daas_framework/doc/2026-08-24-env-prod-merge-into-deploy-conf.md — not in
this doc.

Unblocks issue 9.

## Issue 8 — srv/*.sql grants users to a host-pinned name

Problem: `srv/test.sql` creates `'admin'@'{{servername}}'` (and reader/public).
In prod `{{servername}}` = the section's SERVER = the DB host's ZeroTier IP,
so those users can only connect from that same IP. An app-only server over
ZeroTier uses a different IP and cannot authenticate.

Decision (2026-08-24): **per-host grants, applied manually for now**; a
better mechanism comes later.

- The developer's own db user/host (e.g. `'juan'@'juan-workstation'`) must be
  granted access to the prod databases by hand.
- Tracked as a task in php_daas_framework doc/todo.txt.
- Future mechanism (idea, not started): generate the grants automatically
  from etc/machines.ini — `[dev]` already maps workstation hostname -> DBUSER,
  and `[prod]` maps server -> databases, so the data for automatic per-host
  grants already lives in one place.
- `srv/<dbname>.sql` keeps `{{servername}}` as-is for now (still a prototype
  for building DB servers); ema is not involved in this issue.

## Issue 9 — prod database creation path is undefined

Problem: no repo creates prod databases today — `machines.ini [prod]` is
commented out everywhere, and srv/*.sql application is wired only into the
dev flow. `deploy`/`provision.sh` provisions only the instance (empty
datadir, my.cnf, systemd unit, daemon start) — never databases/users.

Decided model: SSH to the DB host as root and run `ema init db <name>` via
the local socket (root/unix_socket auth). ema already ships to the server
(framework `packages.ema`; simox pulls it). The `[<name>]` section already
exists in /etc/<app>/reuter.ini (gen-reuter writes it regardless of whether
the database exists).

Verified end-to-end (2026-08-24, all three repos):

- `deploy` ships `pkg/`+`srv/` (gitattributes keeps them in the archive) and
  the nix result puts `ema`/`gen-env`/`gen-reuter` on the server PATH.
- `provision.sh` (`deploy --init`, root) creates only the instance (datadir,
  /etc/<instance>/my.cnf, `mariadb@<instance>` unit) — never databases/users.
- `post-nix.sh` (remote hook, root) runs `gen-env` -> `.env`
  (`EMA_TARGET=prod`, `REUTER_INI=/etc/<instance>/reuter.ini`), then
  `gen-reuter "$REUTER_INI"` -> the `[<name>]` section (with
  `MYSQL_UNIX_PORT`) exists on the DB host before any database is created.

Blocker found and fixed (ema, 2026-08-24): `_cmd_init_db`/`_cmd_init_tables`
refused to run as root (`Error: execute without sudo.`), which blocked the
agreed SSH-as-root model. The `EUID=0` guard is now scoped to local mode
only (`[[ $EUID -eq 0 ]] && [ "${EMA_TARGET:-local}" = "local" ]`): root is
allowed in prod mode (the issue-4 root/unix_socket path) and still refused
in dev (keeps the var/ sandbox user-owned). Validated: root+prod passes the
guard, root+local still refuses, normal user unchanged.

Remaining (operational, not code): fill the real ZeroTier IPs into
`etc/machines.ini [prod]` and set `DEPLOY_DB_BIND` + firewall for the DB
port (already tracked in simox doc/todo.txt), then exercise
`ssh root@<db-host> 'cd <deploy-dir> && ema init db <name>'`.

## Fixed facts for future sessions

- Both consumer repos reproduce the same pattern (verified): etc/reuter.ini
  git-ignored with `[local]` (and optionally `[local:<dbname>]`); prod
  `[<dbname>]` sections generated by gen-reuter from etc/machines.ini +
  etc/deploy.conf; local MariaDB instance under var/mariadb; .env generated
  by init-local-env.sh (dev) / gen-env (prod).
- .gitignore (framework + simox): /var/, /etc/reuter.ini, /etc/machines.ini,
  .env.
- prod instance layout (provision.sh): `$DEPLOY_DB_BASE/{data,mysql.sock,
  mysql.pid}` + `/etc/<instance>/my.cnf` + `mariadb@<instance>` systemd unit;
  daemon binds the host's ZeroTier IP on DEPLOY_DB_PORT; prod root =
  unix_socket auth; TCP only (socket-only mode removed).
- Original reuter vision (simox doc/2026-07-10-db-routing.md): one file per
  target at src/reuter/{name}.sh — the INI-with-sections model is the
  evolution of that.
